Customer Cart Module & Atomic Cart-to-Booking Flow Specification | Version 1.0
Base URL: https://api.anjibabujob.com
CRITICAL UX & ARCHITECTURE RULE:
Selecting a service or clicking [Add to Cart] does NOT create a booking in the database! Bookings are created exclusively upon customer confirmation during POST /api/bookings/checkout inside a single atomic @Transactional boundary.

1. Complete End-to-End Workflow

1. Customer Browses Services
   └─ Clicks [Add to Cart] on Electrician (₹499)
      └─ Calls POST /api/cart/items (Backend pulls price from DB, ignores client price)
      └─ ZERO bookings created in DB 🚫

2. Customer Continues Browsing
   └─ Clicks [Add to Cart] on Plumber (₹399)
      └─ Header badge updates via GET /api/cart/count: Cart 🛒 (2)

3. Customer Reviews Cart (GET /api/cart)
   └─ Reviews items:
      - Electrician: 1 × ₹499 = ₹499
      - Plumber: 1 × ₹399 = ₹399
      - Subtotal: ₹898
   └─ Can change quantity (PUT /api/cart/items/{id}) or remove (DELETE /api/cart/items/{id})
   └─ ZERO bookings created in DB 🚫

4. Customer Proceeds to Booking
   └─ Selects saved service address (validated against logged-in customer)
   └─ Selects date & time slot
   └─ Reviews final summary (₹898)

5. Customer Clicks [Confirm Booking]
   └─ Calls POST /api/bookings/checkout
   └─ Entire checkout runs inside a single atomic @Transactional operation:
      1. Validates authenticated customer (X-Customer-Id)
      2. Validates cart items & refreshes live backend prices
      3. Validates address belongs to customer
      4. Creates Booking with status PENDING
      5. Creates BookingItem records for each service line item
      6. Marks Cart as CONVERTED (or clears active items)
      7. Dispatches Worker Matching Engine to send offers to eligible workers
      8. Prevents duplicate bookings from accidental double-clicks

6. Booking Lifecycle Continues Smoothly
   └─ PENDING ➔ WORKER_MATCHING ➔ OFFERED ➔ ACCEPTED ➔ ON_THE_WAY ➔ ARRIVED ➔ Start PIN ➔ IN_PROGRESS ➔ COMPLETED

2. REST API Endpoints Summary

Method Endpoint Description Auth Header
POST /api/cart/items Add service to active cart (ZERO bookings created) X-Customer-Id
GET /api/cart Retrieve active cart, items, subtotal, and total X-Customer-Id
GET /api/cart/count Retrieve live item badge count X-Customer-Id
PUT /api/cart/items/{cartItemId} Update item quantity (0 deletes item) X-Customer-Id
DELETE /api/cart/items/{cartItemId} Remove single item from active cart X-Customer-Id
DELETE /api/cart Clear entire active cart X-Customer-Id
POST /api/bookings/checkout Atomic transactional checkout: creates Booking, BookingItems & dispatches Worker Matching X-Customer-Id, Idempotency-Key

4. Security & Idempotency Rules

  • Price Security: The backend never trusts prices sent from the client. All prices are verified and loaded from the SERVICES table.
  • Customer Ownership Isolation: Cart and items are validated to ensure only the owner can query, update, or remove them. Unauthorized access returns HTTP 403 Forbidden.
  • Address Validation: The checkout process confirms that the provided address belongs directly to the authenticated customer.
  • Double-Click Protection: Accidental repeated submissions using the same Idempotency-Key return the already processed booking immediately without creating duplicate bookings or re-dispatching worker matching offers.
